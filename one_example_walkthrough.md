# Cleaning Robots Example Walkthrough (i=1 and i=2)

This document walks through the `cleaning_robots` R2R benchmark family, which models two competing cleaning robots navigating a linear corridor of rooms. The specification is in the Separated GR(k) format, meaning all assumptions depend only on input variables and all guarantees depend only on output variables.

---

## The Physical Model

Imagine a corridor of N rooms laid out in a line:

```
[Room 0] --- [Room 1] --- [Room 2] --- ... --- [Room N-1]
```

Two robots operate in this corridor:
- The **ENVIRONMENT** robot (input, prefix `in:`) — its behavior is constrained by assumptions, but ultimately chosen by the environment.
- The **SYSTEM** robot (output, prefix `out:`) — this is the robot we are synthesizing a controller for.

Each robot has the following variables:
- `room_i` : Boolean, true if the robot is currently in room i. Exactly one room variable is true at any time (one-hot encoding).
- `clean_i` : Boolean, true if the robot has cleaned room i. Once a room is cleaned, it stays cleaned (monotonic latch).

The environment robot has one extra variable:
- `done` : Boolean, signals that the environment has finished its cleaning task. Once done, it stays done and the environment freezes in place.

**The GOAL** is a reactive game: the system robot must "match" the environment robot's cleaning performance. Specifically, for each room:
- If the environment keeps reporting room i as dirty (`GF !clean_i`) while also signaling done infinitely often (`GF done`), then the system must eventually clean room i (`GF out:clean_i`).
- Conversely, if the environment has cleaned room i (`GF clean_i`) while done, the system must *never* clean it — they divide the work.

---

## i=1: One Room (`cleaning_robots_1.sgrk`)

### Variables

| Type | Variables | Count |
|------|-----------|-------|
| Input | `in:room0`, `in:clean0`, `in:done` | 3 |
| Output | `out:room0`, `out:clean0` | 2 |
| **Total** | | **5** |

### Full Specification

#### Initial Assumptions
```
in:room0 & !in:clean0 & !in:done
```
The environment robot starts in room 0, has not cleaned it, and is not done.

#### Initial Guarantees
```
out:room0 & !out:clean0
```
The system robot starts in room 0 and has not cleaned it.

#### Safety Assumptions (environment transitions)
```
(in:room0) &                                              [A1]
(X in:room0) &                                            [A2]
(in:room0 -> X in:room0) &                                [A3]
((!in:clean0 & X in:clean0) -> (in:room0 & X in:room0)) & [A4]
(in:clean0 -> X in:clean0) &                              [A5]
(in:done -> X in:done) &                                  [A6]
(X in:done -> (X in:room0 <-> in:room0)) &                [A7]
(X in:done -> (X in:clean0 <-> in:clean0))                [A8]
```

| Rule | Meaning |
|------|---------|
| `[A1-A3]` | With only 1 room, the environment robot is always in room 0. Trivially true but generated by the formula pattern. |
| `[A4]` | To clean room 0, the robot must be in room 0 and stay there. |
| `[A5]` | Once cleaned, room 0 stays cleaned (monotonic latch). |
| `[A6]` | Once done, stays done (monotonic latch). |
| `[A7-A8]` | Once done, the environment freezes: room and clean status don't change. |

#### Safety Guarantees (system transitions)
```
(out:room0) &                                              [G1]
(X out:room0) &                                            [G2]
(out:room0 -> X out:room0) &                               [G3]
((!out:clean0 & X out:clean0) -> (out:room0 & X out:room0)) & [G4]
(out:clean0 -> X out:clean0)                               [G5]
```

Same structure as the assumptions but for the system robot:

| Rule | Meaning |
|------|---------|
| `[G1-G3]` | System is always in room 0 (only 1 room). |
| `[G4]` | To clean, must be in the room and stay there. |
| `[G5]` | Once cleaned, stays cleaned. |

#### Fairness (GR(k) winning condition)
```
((GF in:done & GF !in:clean0) -> (GF out:clean0)) &       [F1]
((GF in:done & GF in:clean0)  -> (GF !out:clean0))        [F2]
```

- **`[F1]`** If the environment signals done infinitely often AND room 0 is dirty infinitely often, then the system must clean room 0 infinitely often.
- **`[F2]`** If the environment signals done infinitely often AND room 0 is clean infinitely often, then the system must be "not clean" infinitely often.

> **Important note on `[F2]`:** Since `clean` is a monotonic latch (once clean, always clean), `GF in:clean0` means the environment eventually cleans room 0 and it stays clean forever. In that case, the system is required to have `GF !out:clean0`, meaning it must be "not clean" infinitely often. But once the system cleans a room, it stays clean! So `GF !out:clean0` means the system must **never** clean room 0. This is the "matching" condition: if the environment has already cleaned a room, the system should not bother cleaning it.
>
> Together, `[F1]` and `[F2]` say: for each room, exactly one of the two robots should end up cleaning it. They must **divide the work**.

### Why It Is Realizable (i=1)

With only 1 room, both robots are stuck in room 0. The system can simply choose: if the environment hasn't cleaned room 0 (and keeps signaling done), clean it. If the environment did clean room 0, don't. Since there's only one room and both robots can access it trivially, the system always wins.

**State space:** With 5 Boolean variables, the game graph has at most 2^5 = 32 states (though many are unreachable due to constraints).

## i=2: Two Rooms (`cleaning_robots_2.sgrk`)

### Variables

| Type | Variables | Count |
|------|-----------|-------|
| Input | `in:room0`, `in:room1`, `in:clean0`, `in:clean1`, `in:done` | 5 |
| Output | `out:room0`, `out:room1`, `out:clean0`, `out:clean1` | 4 |
| **Total** | | **9** |

The corridor looks like:
```
[Room 0] --- [Room 1]
```

### Full Specification

#### Initial Assumptions
```
in:room0 & !in:room1 & !in:clean0 & !in:clean1 & !in:done
```
Environment robot starts in room 0. No rooms cleaned. Not done.

#### Initial Guarantees
```
out:room0 & !out:room1 & !out:clean0 & !out:clean1
```
System robot starts in room 0. No rooms cleaned.

#### Safety Assumptions (environment transitions)

**Movement constraints:**
```
(in:room0 | in:room1) &                                   [A1]
(X in:room0 | X in:room1) &                               [A2]
(in:room1 -> !in:room0) &                                 [A3]
(X in:room1 -> !X in:room0) &                             [A4]
```

| Rule | Meaning |
|------|---------|
| `[A1-A2]` | The robot is always in at least one room (current and next step). |
| `[A3-A4]` | At most one room at a time (mutual exclusion). |
| Together | The robot is in **exactly one room** at each step. |

**Adjacency constraints:**
```
(in:room0 -> (X in:room0 | X in:room1)) &                 [A5]
(in:room1 -> X in:room1) &                                [A6]
```

| Rule | Meaning |
|------|---------|
| `[A5]` | From room 0, the robot can stay or move to room 1. |
| `[A6]` | From room 1, the robot **must stay** (end of corridor). |

This means the corridor is a **one-way path: 0 → 1**. The robot can move forward but never backward. Once it reaches room 1, it's stuck.

**Cleaning constraints:**
```
((!in:clean0 & X in:clean0) -> (in:room0 & X in:room0)) & [A7]
((!in:clean1 & X in:clean1) -> (in:room1 & X in:room1)) & [A8]
(in:clean0 -> X in:clean0) &                              [A9]
(in:clean1 -> X in:clean1) &                              [A10]
```

| Rule | Meaning |
|------|---------|
| `[A7-A8]` | To clean room i, must be in room i and stay there. |
| `[A9-A10]` | Once cleaned, stays cleaned. |

**Done/freeze constraints:**
```
(in:done -> X in:done) &                                  [A11]
(X in:done -> (X in:room0 <-> in:room0)) &                [A12]
(X in:done -> (X in:room1 <-> in:room1)) &                [A13]
(X in:done -> (X in:clean0 <-> in:clean0)) &              [A14]
(X in:done -> (X in:clean1 <-> in:clean1))                [A15]
```

| Rule | Meaning |
|------|---------|
| `[A11]` | Once done, stays done. |
| `[A12-A15]` | Once done, everything freezes. |

#### Safety Guarantees (system transitions)

Same structure as assumptions, but for the system robot:

**Movement:** exactly one room, one-hot encoding.
```
(out:room0 | out:room1) &                                 [G1]
(X out:room0 | X out:room1) &                             [G2]
(out:room1 -> !out:room0) &                               [G3]
(X out:room1 -> !X out:room0) &                           [G4]
```

**Adjacency:** one-way corridor 0 → 1.
```
(out:room0 -> (X out:room0 | X out:room1)) &              [G5]
(out:room1 -> X out:room1) &                              [G6]
```

**Cleaning:** must be present in room to clean, cleaning is permanent.
```
((!out:clean0 & X out:clean0) -> (out:room0 & X out:room0)) & [G7]
((!out:clean1 & X out:clean1) -> (out:room1 & X out:room1)) & [G8]
(out:clean0 -> X out:clean0) &                            [G9]
(out:clean1 -> X out:clean1)                              [G10]
```

> **Note:** The system robot has **no** `done` variable and **no** freeze constraint. It keeps operating forever.

#### Fairness (GR(k) winning condition)
```
((GF in:done & GF !in:clean0) -> (GF out:clean0)) &       [F1]
((GF in:done & GF !in:clean1) -> (GF out:clean1)) &       [F2]
((GF in:done & GF in:clean0)  -> (GF !out:clean0)) &      [F3]
((GF in:done & GF in:clean1)  -> (GF !out:clean1))        [F4]
```

| Rule | Meaning |
|------|---------|
| `[F1]` | If environment is done & room 0 is dirty → system must clean room 0. |
| `[F2]` | If environment is done & room 1 is dirty → system must clean room 1. |
| `[F3]` | If environment is done & room 0 is clean → system must NOT clean room 0. |
| `[F4]` | If environment is done & room 1 is clean → system must NOT clean room 1. |

In words: the two robots must **divide the rooms** between them. Each room is cleaned by exactly one robot. The system must figure out which rooms the environment left dirty and clean those, while leaving the environment-cleaned rooms alone.

## The Key Challenge With i=2

The corridor is one-way: both robots start in room 0 and can only move forward (room 0 → room 1). Once a robot moves to room 1, it can never return to room 0.

This creates a **strategic dilemma** for the system robot:

| Scenario | Environment behavior | System obligation | Strategy |
|----------|---------------------|-------------------|----------|
| **A** | Cleans room 0 first, then moves to room 1 | Don't clean 0 (`F3`), must clean 1 (`F2`) | Move to room 1 without cleaning room 0 |
| **B** | Moves to room 1 without cleaning room 0 | Must clean 0 (`F1`), don't clean 1 (`F4`) | Stay in room 0, clean it, then move on |
| **C** | Cleans both rooms | Don't clean either | Just move through without cleaning |
| **D** | Cleans neither room | Must clean both | Clean room 0, then move to room 1 and clean it |

The system robot cannot go back. So it must decide: *do I clean room 0 now, or skip it and move on?* It needs to **observe** what the environment robot is doing (via the input variables) and react accordingly.

The critical insight is that the system can **wait** in room 0 to see whether the environment cleans it. Since the environment must signal "done" eventually (otherwise the fairness conditions are vacuously satisfied), the system can use the "done" signal plus the clean status to decide what to do.

---

## Why It Is Realizable (i=2)

A winning strategy for the system robot with 2 rooms:

1. **Start** in room 0 (required by initial guarantee).
2. **Wait** in room 0. Observe the environment.
3. **When the environment signals "done":**
   - If `in:clean0` is false → clean room 0 (stay in room 0 for one step to trigger the clean), then move to room 1.
   - If `in:clean0` is true → don't clean room 0, move to room 1.
4. **Once in room 1:**
   - If `in:clean1` is false → clean room 1.
   - If `in:clean1` is true → don't clean room 1.

Since "done" freezes the environment, the system can safely read the final state and act on it. The system never needs to go backwards because it processes rooms in order, making decisions as it goes.

## Scaling: i=1 vs i=2

| | i=1 | i=2 |
|---|-----|-----|
| Rooms | 1 | 2 |
| Input variables | 3 | 5 |
| Output variables | 2 | 4 |
| Total variables | 5 | 9 |
| Spec lines | 20 | 38 |
| Fairness pairs | 2 | 4 |
| Max states (2^vars) | 32 | 512 |
| Movement constraints | trivial | one-way corridor |
| Strategic complexity | none | must observe & decide |
| Result | Realizable | Realizable |

The jump from i=1 to i=2 introduces the fundamental challenge of the benchmark: the system must make **irreversible movement decisions** (one-way corridor) based on observations of the environment. At i=1 there is no movement decision at all. At i=2, the system must decide when to leave room 0, and whether to clean it before leaving.

At larger i, this gets harder: the system robot traverses a longer one-way corridor, and at each room must decide whether to clean it or skip it, based on what the environment robot has done. The state space grows exponentially (2^(4i+1) for input+output variables), making synthesis progressively more challenging.

---

## How the Tool Solves It

The SGR(k) tool exploits the "separated" structure of the specification: assumptions only mention input variables, guarantees only mention output variables. This separation allows the tool to decompose the problem:

1. **Build the game graph:** The input and output transition relations are compiled into BDDs independently, then combined.
2. **Compute strongly connected components (SCCs):** The game graph is analyzed for its SCC structure using the CycleCover algorithm.
3. **Solve the weak game:** The GR(k) winning condition (which GF pairs must be satisfied) is checked within each SCC. A state is winning if the system can force the game into an SCC where all fairness conditions are met.
4. **Extract strategy:** From winning states, the tool computes a transition relation that guides the system from any winning state to a winning SCC and keeps it there.

Because of the separation property, the game graph has a product structure that the BDD operations can exploit, achieving linear-time complexity in the number of game states (rather than the cubic worst case of general GR(1) synthesis).

The tool outputs three BDDs:
- **FG(CC):** the set of winning states (from where the system can force the game into a good SCC and stay there forever).
- **CC:** states within a winning SCC (where the system can satisfy the GR(k) condition without leaving the component).
- **T:** a transition relation guiding the system from winning-but-not-CC states into CC states.

---

## Result

Both `cleaning_robots_1` and `cleaning_robots_2` are **REALIZABLE**. The system robot can always observe the environment's cleaning decisions and react appropriately, dividing the rooms between the two robots.
